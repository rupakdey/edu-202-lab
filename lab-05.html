Configure AppProtection in ZPA

Publish DVWA, apply an AppProtection profile, and compare logged Allow behavior with Block enforcement.

4 tasks Approx. 30 minutes Dedicated tenant
Lab objectives

What you will accomplish

  • Publish DVWA and add its internal DNS record.
  • Create an AppProtection profile and Inspect policy.
  • Run the supplied SQLi/XSS tests and correlate behavior with diagnostics.
Technical context

What AppProtection adds to ZPA

ZPA and ZIA solve different problems. ZIA is designed for Internet/SaaS traffic and performs inline security inspection at its Service Edge. ZPA is designed to connect an authorized user to a specific private application; the base ZPA Service Edge brokers the connection and does not inspect the application payload by default. AppProtection adds application-layer inspection to selected ZPA private web applications.

Internet & SaaS

ZIA: inspect traffic going outward

Typical destination: Internet and SaaS applications.

Core role: proxy/forward traffic through an inspection Service Edge and apply Internet security controls.

ZIA can also inspect selected ZPA application traffic through the separate Inspect Traffic with Internet & SaaS capability. That is not what this lab is configuring.

Private applications

ZPA + AppProtection: protect the private app transaction

Typical destination: private HTTP/HTTPS applications reached through ZPA.

Core role: ZPA first decides whether the user may reach the application. AppProtection can then inspect the authorized web transaction before it reaches the backend application.

This is application-centric protection: the primary object being protected is the private web application, including against malicious requests from compromised or otherwise authorized users.

Control

One detection rule

A control identifies a specific suspicious condition or attack pattern and has properties such as severity, paranoia level, and an action. Control families include OWASP predefined, ThreatLabZ, API, WebSocket, and custom controls.

AppProtection Profile

Which controls + how they behave

The profile groups controls, selects the OWASP CRS version, sets the paranoia level/execution behavior, and defines common or overridden actions such as Allow, Block, or Redirect.

AppProtection Policy

Where the profile applies

The policy matches criteria such as an application segment, user/device context, or identity attributes, then chooses Inspect or Bypass Inspection and associates the appropriate AppProtection profile.

What it can detect

Web-application attack patterns

SQL injectionCross-site scripting (XSS)Path / file traversalProtocol anomaliesKnown CVE patternsAPI violationsWebSocket threats

The exact coverage depends on which control families and individual controls are enabled in the profile.

OWASP Core Rule Set

Reusable WAF-style rules

The OWASP Core Rule Set (CRS) is a generic set of web-application firewall rules for detecting common application attacks. In this lab, the predefined OWASP controls are intentionally used against DVWA so you can generate SQL injection and XSS events and watch AppProtection detect them.

OWASP paranoia level

Higher level = more aggressive detection and more tuning

Paranoia Level controls how many OWASP CRS rules participate in detection. It is not the same thing as severity. Severity describes the significance of an individual control; paranoia changes how aggressively the rule set looks for suspicious input.

PL1BaselineLeast strict · low false-positive rate
PL2ElevatedMore rules · some tuning expected
PL3StrictSpecialized/aggressive rules · more false positives
PL4Most strictMaximum coverage · substantial tuning likely

Lab choice: EDU-202 uses PL3 so the deliberately vulnerable DVWA application produces useful detection events. In production, choose a level based on application risk and test/tune legitimate traffic before enforcing broadly.

i
How the lab demonstrates enforcement

The profile starts with the selected controls set to Allow. The SQLi/XSS requests still reach DVWA but are recorded in AppProtection diagnostics. You then change the control action to Block and repeat the same attack to prove that AppProtection can stop the transaction before the backend application accepts it.

i
Existing context — two different DNS jobs

The Browser Access external domain gets the browser to ZPA. Separately, the App Connector resolves dvwa-<XYZ>.patraining.safemarch.com through internal DNS to 10.0.0.128 and connects to the container on TCP 80. DNS returns an address; it does not forward HTTP. The Docker host is 10.0.0.2, while this lab’s DVWA container has its own address.

5.2

Create the AppProtection Profile

Start with Allow overrides so detected attacks can be logged.

Private Access›Private App Protection›Policy›Protection Profiles›AppProtection

Documented route; portal menu versions can differ. Search by the feature name if needed.

Search Menu → Protection Profiles
Zscaler Help: Protection Profiles ↗
  1. On the AppProtection tab select Add. Name the profile DVWA_Protection_Profile; description is optional.
  2. Under Controls, select OWASP_CRS/4.8.0 and all its predefined controls. Select all available ThreatLabZ, WebSocket, and API controls, as specified in the lab.
  3. Select Next. Set Predefined Paranoia Level to 3.
  4. Under Override Controls, choose Override All Controls. Set Transaction → Allow for the listed OWASP, WebSocket, ThreatLabZ, API and Active Directory control families. Review and Save.
✓
Expected result

DVWA_Protection_Profile is saved at paranoia level 3 with the lab’s selected controls and Allow overrides.

5.4

Compare Allow and Block Behavior

Run the source lab’s DVWA tests and inspect matching events.

  1. Log out of ZCC. Open Browser Access in the Experience Center and copy the External Domain for your DVWA entry. Open it with https://, authenticate to the lab identity service if prompted, then sign in to DVWA as admin / password.
    Search Menu → Browser Access
    Zscaler Help: Browser Access ↗
  2. If DVWA requests initialization, select Create / Reset Database, then sign in again.
    !
    Training database reset

    This resets the DVWA training data. Use it only inside the assigned DVWA lab instance.

  3. Select SQL Injection. In User ID, enter the supplied test, then Submit.
    1' or '1'='1
  4. Select XSS (Stored). Enter Name: JSAttack and the message below, then Sign Guestbook.
    <script>alert("You've been HACKED!")</script>
  5. Use Search Menu → Private Diagnostics. Set Log Type → AppProtection, then review Security Profile Violations. Correlate the DVWA application, profile, time and Allow action with your tests.
  6. Edit DVWA_Protection_Profile. Change the relevant override control actions from Allow to Block and Save.
  7. Reopen DVWA and repeat the same SQL injection. Confirm the request is blocked, then correlate the new event and Block action in Private Diagnostics → AppProtection.
✓
Expected result

Allow-mode attacks reach DVWA and create matching diagnostics; after changing to Block, the repeated test is denied with a corresponding Block event.
