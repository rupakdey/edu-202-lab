Configure AppProtection in ZPA

Protect the intentionally vulnerable DVWA application with ZPA AppProtection. You will publish the application, build a protection profile, apply it, generate sample SQLi/XSS events, and compare report-only versus blocking behavior.

4 tasksApprox. 30 minutes
Lab objectives

What you will accomplish

  • Configure application segments and access policies for protected resources.
  • Create AppProtection profiles to manage security posture and enforcement levels.
  • Apply AppProtection policies to specific application segments.
  • Validate security enforcement and monitor violations through diagnostics.
Technical context

What AppProtection adds to ZPA

ZPA and ZIA solve different problems. ZIA is designed for Internet/SaaS traffic and performs inline security inspection at its Service Edge. ZPA is designed to connect an authorized user to a specific private application; the base ZPA Service Edge brokers the connection and does not inspect the application payload by default. AppProtection adds application-layer inspection to selected ZPA private web applications.

Internet & SaaS

ZIA: inspect traffic going outward

Typical destination: Internet and SaaS applications.

Core role: proxy/forward traffic through an inspection Service Edge and apply Internet security controls.

ZIA can also inspect selected ZPA application traffic through the separate Inspect Traffic with Internet & SaaS capability. That is not what this lab is configuring.

Private applications

ZPA + AppProtection: protect the private app transaction

Typical destination: private HTTP/HTTPS applications reached through ZPA.

Core role: ZPA first decides whether the user may reach the application. AppProtection can then inspect the authorized web transaction before it reaches the backend application.

This is application-centric protection: the primary object being protected is the private web application, including against malicious requests from compromised or otherwise authorized users.

Control

One detection rule

A control identifies a specific suspicious condition or attack pattern and has properties such as severity, paranoia level, and an action. Control families include OWASP predefined, ThreatLabZ, API, WebSocket, and custom controls.

AppProtection Profile

Which controls + how they behave

The profile groups controls, selects the OWASP CRS version, sets the paranoia level/execution behavior, and defines common or overridden actions such as Allow, Block, or Redirect.

AppProtection Policy

Where the profile applies

The policy matches criteria such as an application segment, user/device context, or identity attributes, then chooses Inspect or Bypass Inspection and associates the appropriate AppProtection profile.

What it can detect

Web-application attack patterns

SQL injectionCross-site scripting (XSS)Path / file traversalProtocol anomaliesKnown CVE patternsAPI violationsWebSocket threats

The exact coverage depends on which control families and individual controls are enabled in the profile.

OWASP Core Rule Set

Reusable WAF-style rules

The OWASP Core Rule Set (CRS) is a generic set of web-application firewall rules for detecting common application attacks. In this lab, the predefined OWASP controls are intentionally used against DVWA so you can generate SQL injection and XSS events and watch AppProtection detect them.

OWASP paranoia level

Higher level = more aggressive detection and more tuning

Paranoia Level controls how many OWASP CRS rules participate in detection. It is not the same thing as severity. Severity describes the significance of an individual control; paranoia changes how aggressively the rule set looks for suspicious input.

PL1BaselineLeast strict · low false-positive rate
PL2ElevatedMore rules · some tuning expected
PL3StrictSpecialized/aggressive rules · more false positives
PL4Most strictMaximum coverage · substantial tuning likely

Lab choice: EDU-202 uses PL3 so the deliberately vulnerable DVWA application produces useful detection events. In production, choose a level based on application risk and test/tune legitimate traffic before enforcing broadly.

i
How the lab demonstrates enforcement

The profile starts with the selected controls set to Allow. The SQLi/XSS requests still reach DVWA but are recorded in AppProtection diagnostics. You then change the control action to Block and repeat the same attack to prove that AppProtection can stop the transaction before the backend application accepts it.

6.1

Create the DVWA Application Segment

Publish DVWA and create the supporting access and DNS configuration.

  1. On Corp: Client PC 1, open App Segments and select Add Application Segment.
    Search menu → App Segments
  2. Configure the DVWA application:
    SettingValue
    NameDVWA
    Applicationdvwa-<XYZ>.patraining.safemarch.com
    Access TypeBrowser Access and App Protection
    Certificate TypeManaged
    External URLPrefix dvwa; choose any available suffix
    Internal URLHTTP / 80
    Client Connector AccessDefault Port Range = Web Server
    Segment GroupCorpApps
    Server GroupCorpServers

    XYZ is the last three digits of your tenant ID. Example: ZS000205 → dvwa-205.patraining.safemarch.com.

    Review and save.
  1. Create an Access Policy rule named dvwa_allow_policy with action Allow Access and application criteria DVWA. Save it.
    Search menu → Access Policy
  1. On Corp: Win Svr, open Server Manager → Tools → DNS. In the patraining.safemarch.com forward lookup zone, create a new Host (A) record.
  2. Set Name = dvwa-<XYZ> and IP address = 10.0.0.128, then add the host. The FQDN is populated automatically.
Why this DNS record matters

Why does DVWA resolve to 10.0.0.128 instead of the Docker host 10.0.0.2?

The Browser Access External Domain is the user-facing name that brings the user to ZPA. The internal FQDN dvwa-<XYZ>.patraining.safemarch.com serves a different purpose: the App Connector resolves it through corporate DNS so it can reach the real DVWA backend. In this lab, the DVWA container itself owns 10.0.0.128:80, so the A record must resolve to that address rather than the Docker host IP.

DNS does not forward HTTP

It only resolves the destination

The A record maps the internal application FQDN to 10.0.0.128. After resolution, the App Connector opens the actual backend connection to 10.0.0.128:80.

Why not 10.0.0.2?

The container owns the application IP

10.0.0.2 is the Docker host. The DVWA container is reachable at 10.0.0.128 on the lab Docker network, and the lab is not relying on a host-side published port to proxy 10.0.0.2:80 to the container.

  1. Confirm the DNS entry exists. Allow roughly 3–5 minutes for the change to propagate in the lab environment.
✓
Expected result

The DVWA application segment, access policy, and internal DNS record are in place.

6.2

Set Up the AppProtection Profile

Select security controls and begin in report-only behavior.

  1. Open Private App Protection → Protection Profiles and select Add.
    Search menu → Protection Profiles
  2. Create a profile named DVWA_Protection_Profile. Description is optional; select Next.
  1. On Controls, select OWASP_CRS/4.8.0 and select all controls in that set. Also select all controls under ThreatLabZ, WebSocket, API, and Active Directory controls.
  1. Set Predefined Paranoia Level = 3. PL3 enables a stricter OWASP CRS rule set than PL1/PL2 and is more likely to require false-positive tuning in production.
  2. Under Override Controls, choose Override All Controls and set the transaction action to Allow for the selected control families. Continue and save the profile.
✓
Expected result

DVWA_Protection_Profile contains the selected security controls but initially allows matching traffic so attacks can be observed and logged.

6.3

Apply the AppProtection Policy

Attach the protection profile to the DVWA application.

  1. Open Private App Protection → Protection Policies and select Add.
    Search menu → Protection Policies
  2. Configure:
    SettingValue
    NameDVWA_AppProtection_policy
    DescriptionOptional
    Rule ActionInspect
    AppProtection ProfileDVWA_Protection_Profile
    Application criteriaDVWA
    Save the policy.
✓
Expected result

Traffic to the DVWA application is inspected using DVWA_Protection_Profile.

6.4

Test and Verify AppProtection

Generate attacks, inspect the logs, switch to Block, and retest.

  1. Log out of Zscaler Client Connector on Corp: Client PC 1. Open the Experience Center, locate Browser Access, and copy the External Domain for the DVWA application.
    Search menu → Browser Access
  2. Open the External Domain in a new browser session, authenticate with the lab-access identity if prompted, then sign in to DVWA with admin / password.
  3. Select Create / Reset Database. After the reset, sign in to DVWA again.
  1. Run the SQL Injection test: open SQL Injection, enter 1' or '1'='1 in User ID, and submit. The attack should succeed because the control action is currently Allow.
  2. Run the stored XSS test: open XSS (Stored), set Name to JSAttack, enter <script>alert("You've been HACKED!")</script>, and select Sign Guestbook.
  1. Open Private Application Diagnostics, set Log Type = AppProtection, and review Security Profile Violations. Confirm the attacks were logged while still reaching the application.
    Search menu → Diagnostics
  2. Edit DVWA_Protection_Profile and change the selected control action from Allow to Block.
  1. Return to DVWA and repeat the SQL injection test.
  2. Confirm the malicious request is now blocked, then return to AppProtection diagnostics and verify the blocked event appears in Security Profile Violations.
✓
Expected result

The same test attack is first allowed/logged in report-only mode and then blocked/logged after the protection profile action changes to Block.

✓
